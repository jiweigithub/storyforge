> 服从项目总纲 §6、§7、§11 和上层产品共同契约；本文细化角色聊天的施工顺序，不改变其它产品边界。

目标是让玩家与有稳定人格、各自知识、记忆和目标的角色共同发展故事。玩家可只提供一个矛盾或场景，系统补足可演绎的情境；角色依自身动机行动，玩家可以接受、拒绝或改变方向，实际后果持续影响后续。玩家也可直接进入预置情境，或由角色从共同经历发起下一件事，不必不断替角色编剧情。

核心路径为：情境种子 → 有背景和发展可能的情境 → 分角色视角 → 角色行动与玩家参与 → 后果提交 → 情境更新。先交付单角色的完整路径，再扩展长期关系与多人互动，随后完善表现、发行和商业服务。

查阅进度：第 3 节看阶段和里程碑，第 4 节按稳定编号勾选开发步骤，第 7 节查体验验收，第 8 节查状态与证据更新规则。计划修订不计为功能开发完成。

“超过酒馆”须由同等模型条件下的用户体验与长期质量验证支持。底层注册表、测试数量或 commercialReady 标志都不是竞争优势或商业成熟度证明。

### 2.1 有意义的主动推进

主动推进至少具有可说明的动机或情境原因，改变有用信息、关系、目标、可选行动或未解决问题中的一项，并在相关后续中产生影响。重复追问玩家想做什么、换措辞重提被拒绝建议、随机制造与既有事情无关的危机，不算有效推进。兑现承诺、澄清误会、共同安排和阶段性收束也算推进，不要求每轮出现矛盾或反转。

剧情互动与轻松伴聊使用不同节奏。情境复杂度以能支撑当前互动为限：首个切片先验证一条主要未完成事项和必要的人际张力，后续再扩展多线；不能把复杂度、发言量或新事件数量当质量指标。休息、沉默和暂时搁置可以是合理行为。

### 2.2 情境与角色演绎的职责

情境是可持久化、可检查的产品状态，不依赖模型未保存的内部推理，也不是预先写好的完整剧情树。逻辑合同先于表设计，优先扩展已有事件、检查点和上下文设施。

| 内容 | 最小语义与限制 |
|---|---|
| 情境种子 | 来自玩家明确设置的情景、体验包初始内容或角色的既有目标/承诺；记录来源。普通角色台词、猜测和玩笑不能自动成为改写世界的授权 |
| 背景与事实 | 当前时地、参与者、已确定的原作/私域事实、信息差和行动条件；区分已知、未定与角色猜测。已确定的幕后真相不能为了反转被静默重写 |
| 角色动机 | 当前目标、价值取舍、顾虑、底线、关系、已知信息和可能错误的判断；具体行动由角色选择，不统一套用推进话术 |
| 剧情线 | 稳定身份、起因和因果事件、涉及者及可见性、当前进展、待解决问题、可满足的收束条件；支持推进、受阻、搁置、解决、放弃或转化，不预设必达结局 |
| 行动与后果 | 区分意图、提出、尝试与已成立结果；记录行为主体、权限、前置状态、来源事件、见证者、实际变化及后续影响。未选候选没有事实效力 |
| 发展可能 | 下一步机会、压力与备选方向均可调整；不能当作已经发生的事实或把用户强送回固定路线。时间推进须有会话规则和事件依据，不按模型随口描述扣除时间 |

一次有界运行按以下顺序工作：读取当前情境与相关未完成事项 → 选择继续、行动、留白或收束 → 按角色权限组装视角 → 角色表达或尝试行动、等待必要的玩家选择 → 校验并提交实际后果 → 更新情境与后续打算。每次执行到需要玩家决定、任务完成、停止或预算上限即交还控制；不为实现主动性伪造玩家消息。

剧情收束后，新的真实玩家消息仍可得到一次角色回应。若该角色没有 active/paused 目标，行动可明确不绑定目标；此时不得改动旧目标或剧情线、创建新打算或请求新情境，但实际动作、披露与关系后果仍走同一审查及原子提交。回复后交还控制，不自动补满轮次；主动接续仍须有未完成事项，新剧情通过现行情境路径建立。不能为了普通聊天捏造目标，也不能把结束剧情等同于结束角色交流。

情境构建与节奏调度、角色演绎、后果校验是三种职责，不预先要求三个 Agent 或每轮三次模型调用。仅在新情境、重要事件、目标变化、受阻等需要时重估局面；一般交谈复用当前状态。角色只读自己的视角，调度结果不得夹带另一角色的秘密。情境服务也只能读取合同获准的材料，不能把全部作者全知或未来结局自动装入上下文。

叙述和状态必须一致：台词可以是谎言或猜测，旁白宣告发生的动作则须与获准提交的事件相符。系统可对越权、版本、幂等与状态机做确定性校验；动机是否自然、剧情是否好看仍需语义评估和真人试玩，不能声称 parser 能保证文学质量。

V32 收束后回应修复已通过 11 文件/174 项定向检查及 2 条隔离浏览器路径：手动、自然与轮流调度只回应可听见的新消息一次，拒绝旧触发、旧未审查事件、已排除消息和借空目标扩展剧情；刷新、分支、导入与结果未知不重发得到检查。新目标标识允许显式空值，历史字符串合同保持不变，无新表、迁移或世界回写。初验测试漏设纯状态样本预算，并把分支重映射后的事件序号误与父会话比较；修正测试后通过，未放宽运行规则。真实模型复验结果见下；完整 CI/E2E 尚待终态结果，M1 与商业验收不因此完成。

### 2.4 最小体验样例

守卫可主动提议检查后门。玩家同意、拒绝、提供新线索或改为修路离开，应产生有因果差异的后续；系统记录实际发现及关系影响，不把提议等同于行动完成。刷新后仍承接同一局面，阶段解决后能够停下来。固定路线只能作为工程夹具，不能代替开放选择的体验验收。

- 后果：绑定被采用的行动/消息、实际发生事件、见证者、事实/知识/关系/剧情线变化、后续机会及预算证据；确定性系统生成事件身份与版本，重试幂等，编辑分支后失效范围可追溯。
- 版本与迁移：新合同先作为聊天专用版本化附属模块，缺少模块的旧包不启用新主动叙事；不改变其它产品的运行含义。旧存档继续绑定原 release，显式副本迁移只整理已发生事实。

### 7.1 主动叙事测试与判定

按完整互动片段评分，不按单句是否出现新事件计数。同一情境比较不同用户选择时，保持初始事实、角色配置与模型条件可比；只改待测试的选择策略。剧情可以出现合理的共同结果，但不能抹掉选择造成的路径、关系或信息差异。

| 场景/行为 | 验证内容 | 失败例 |
|---|---|---|
| 用户只给种子或简短回应 | 角色能从已有局面提出有动机的行动，交还必要选择 | 不停问“你想怎么办”，要求玩家继续编故事 |
| 用户拒绝建议 | 角色调整、暂缓或采取有权限的独立行动，拒绝得到承接 | 换措辞反复推同一建议，直接叙述玩家答应 |
| 用户另提方法或主动带剧情 | 角色能参与、补充或有理由地反对，后续存在相应差异 | 无视新方案，继续念固定提纲 |
| 用户转话题或希望轻松相处 | 节奏降低；旧事可搁置，在有依据时再续 | 每隔几轮制造危机或强制催办 |
| 用户回到旧话题/跨场景重逢 | 已发生后果和未完成事项影响下一次行动，已解决问题不重复开局 | 忘记承诺、重新生成不同背景/真凶 |
| 用户作出计划外选择、情境受阻 | 依据既定事实寻找合理行动、说明限制或允许收束 | 为保住结局临时改历史、无依据增加线索/敌人 |
| 误认、隐瞒与知识变化 | 区分主张与事实，角色只因见证/披露更新知识 | 角色因系统拥有秘密就突然全知 |
| 候选切换、编辑、取消与刷新 | 文本、行动和后果一致；未选/未提交内容不留副作用 | 展示新回复却沿旧剧情走，刷新丢失结果 |
| 多角色目标分歧（CHAT-06） | 各自行动、私聊和转述形成可追溯的互动 | 全员同一立场、重复信息或泄露未见秘密 |

### 8.1 每次开发后的进度更新

第 3 节工作包状态、第 4 节勾选步骤是本计划的进度入口；PR、commit 和测试/试玩记录是证据来源，长期已交付能力同步到 CAPABILITY-BASELINE。每次交付同时更新受影响状态，只记录当前结果与必要链接，不把原始调用日志或聊天流水塞进计划。

更新时依次检查：本次完成哪些步骤 → 对应合同/UI/生命周期是否完整 → 哪些工程和体验门已验收 → 是否具备勾选证据 → 下一个步骤及阻塞原因。需要体验验收的步骤仅有代码或自动测试时标为待验收；所需真人/真实模型验证未做仍未完成。纯合同/检查步骤按其适用证据验收，不强加无关试玩。文档修订、示例和 mock 不作为新功能证据。

证据附在对应步骤后，使用以下紧凑格式；没有阻塞写“无”，没有完成证据保持未勾选：

```text
步骤：CHAT-02.08
状态：进行中 / 待验收 / 阻塞 / 已验收
交付：用户可见变化；PR/commit 链接
验证：适用检查、真实模型/人工样本、结果与证据位置
未完成/阻塞：具体问题；所需条件
下一步：稳定步骤 ID
更新日期：YYYY-MM-DD
```

用户更新日志只写已交付、可使用的变化；规划不冒充上线。本计划完成的阶段将稳定规则归并产品契约，避免长期保留失真的施工流水。
